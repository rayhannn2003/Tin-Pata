# Android Release

Workflow: `.github/workflows/android-release.yml`. Builds a sideload release APK on
a GitHub-hosted Ubuntu runner. **Not EAS Build** — Gradle runs directly in CI.

## Triggers

| Trigger | Result |
|---|---|
| Push a `v*` tag | Builds and publishes a **GitHub Release** with the APK attached |
| Manual (`workflow_dispatch`) | Builds and uploads a **GitHub Actions artifact** named `tin-pata-apk` (14-day retention) |

```bash
# Tagged release
git tag v2.2.0
git push origin v2.2.0
```

Version name comes from the tag on a tag build, and from `package.json` (prefixed
`v`) on a manual run. The APK is never deployed to the VPS.

## What the pipeline does

```
checkout → Node 20 → Java 17 → Android SDK
  → npm ci
  → write .env from EXPO_PUBLIC_* secrets   (+ assert no server secrets)
  → npm run typecheck                        (blocking)
  → npx expo-doctor                          (blocking)
  → npx expo prebuild --platform android     (android/ is not committed)
  → patch gradle.properties (JVM memory)
  → patch build.gradle (ndk debugSymbolLevel "NONE")
  → ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a
  → collect, measure, report composition
  → GitHub Release (tag) or artifact (manual)
```

### CNG

`android/` and `ios/` are git-ignored and generated by `expo prebuild` in CI. The two
native patches (Gradle memory, debug symbols) are therefore applied **after**
prebuild — committing the generated folder just to hold them would defeat CNG.

Both patches are written to be re-runnable: the `sed` for `org.gradle.jvmargs` deletes
any existing line before appending, so the file cannot end up with two.

## ABI: arm64-v8a only

```bash
./gradlew assembleRelease --no-daemon -PreactNativeArchitectures=arm64-v8a
```

This is a deliberate sideload build for modern physical devices. It **excludes**:

```
armeabi-v7a    x86    x86_64
```

So it will not install on pre-2017-era 32-bit handsets, and will not run on most
emulators (which are x86_64). For a Play Store release, build an **AAB** instead and
let Play split per-device — do not ship this APK there.

## Size

Target: **≤ 25 MB**, enforced as a warning, not a failure:

```
::warning::APK size is 31.2 MB, above the 25 MB target.
```

The build is not failed on size in this first implementation — add a hard budget once
a few real numbers exist. Tin Pata bundles `react-native-pdf` and
`react-native-blob-util`, so it is expected to be heavier than a plain Expo app; the
14 MB achieved on a different project is not a promise here.

The measured size is printed, written to `$GITHUB_ENV` for the release notes, and
added to the workflow run summary.

### Optimizations applied

In `app.json` under `expo-build-properties`:

| Flag | Effect |
|---|---|
| `enableProguardInReleaseBuilds` | Strips unused Java/Kotlin |
| `enableMinifyInReleaseBuilds` | Minifies bytecode |
| `enableShrinkResourcesInReleaseBuilds` | Drops unreferenced resources |
| `enableBundleCompression` | Compresses the JS bundle |
| `useLegacyPackaging` | Compresses native libs in the APK |
| `enableWebpSupport: false` | Drops WebP decoding |

`enableWebpSupport: false` was verified safe before enabling — `find assets -iname
'*.webp'` returns nothing. **Re-check that if WebP assets are ever added**, or images
will silently fail to decode.

Hermes stays **enabled**. Do not switch JS engine for size — it costs startup time and
bytecode precompilation.

`ndk { debugSymbolLevel "NONE" }` is patched into the release build type: full native
symbols bloat the download and the merge step can exhaust runner memory.

### Analysing size

The workflow prints the 30 largest entries and per-directory totals. Locally:

```bash
# Largest individual entries
unzip -l app.apk | sort -k1 -n | tail -30

# What to look at
#   lib/arm64-v8a/   native libraries (PDF, blob-util, Hermes, RN core)
#   assets/          the JS bundle (index.android.bundle) and fonts
#   res/             images, layouts, drawables
#   classes*.dex     Java/Kotlin bytecode after ProGuard
```

Android Studio → **Build → Analyze APK…** gives the same breakdown interactively,
including raw vs download size per entry.

## Secrets

Only values safe to embed in an APK:

```
EXPO_PUBLIC_SUPABASE_URL
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY
EXPO_PUBLIC_API_URL
```

Anything prefixed `EXPO_PUBLIC_` is **bundled into the APK and readable by anyone who
installs it**. `OPENAI_API_KEY` and `SUPABASE_SERVICE_ROLE_KEY` must never appear
here — the app reaches AI only through the backend, which holds the key server-side.
The workflow fails the build if `.env` matches `OPENAI` or `SERVICE_ROLE`.

## Signing

The build currently signs with the **debug** keystore (Expo's prebuild default).
That is fine for sideloading, but every APK from a differently-generated keystore is
treated as a different app by Android — users may have to uninstall before updating.

For stable upgrades, generate a release keystore, store it as a base64 GitHub secret,
decode it in CI, and point `signingConfigs.release` at it. Not configured yet.

